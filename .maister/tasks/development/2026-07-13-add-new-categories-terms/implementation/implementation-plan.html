TL;DR

4 task groups, organized by concern rather than by layer/specialty (single-repo, low-risk, mechanical change, no new files or components). Group 1 (Taxonomy Mechanism) lands first; Group 2 (FilterBar UX + its BrowseGrid tests) depends on it; Group 3 (Documentation Sweep) is fully independent and can run in parallel with 1–2; Group 4 (Test Review & Gap Analysis) depends on all three and closes one coverage gap the spec's Core Requirements leave untested. 30 steps total, 5 tests total (4 spec-minimum + 1 planner-added gap fix).

Key Decisions

  • Groups organized by concern (Taxonomy / FilterBar UX / Docs / Test Review), not role/specialty — a database/API/frontend split would be artificial for this scope.
  • Group 3 (Documentation Sweep) has no dependency on Groups 1–2: every replacement is a literal number swap or (for architecture.md:30) fully specified by the spec's own CR6 description. No shared files — safe to run concurrently.
  • FilterBar.ts is edited in both Group 1 (taxonomy literals + comment) and Group 2 (chip-count constant, renderChips(), reset()) — declared in both groups; Group 2 depends on Group 1 regardless, since its rewritten test targets a category that must exist first.
  • BrowseGrid.test.ts's taxonomy-count and FilterBar-visible-count test edits (Test A, Test B, new collapse test) stay together in one group (Group 2) — splitting them would leave an intermediate broken-test state.
  • Group 1's test footprint is intentionally 1 test, not padded to 2–8: a mechanical literal-list/comment update with exactly one direct unit-test touchpoint. Broader correctness verified via tsc -b and npm run validate-glossary instead of synthetic tests.
  • Group 4 adds 1 test beyond the spec's named minimum: the Success Criteria bullet “'Clear filters' collapses an expanded chip list” (CR8) has no CR10–12-assigned automated check — the same shape of gap verification/spec-audit.md Finding 4 already caught for a sibling requirement. Closed in Group 4 (the designated gap-analysis group) so Group 2's test list still matches the spec's explicit minimum 1:1.

Open Questions / Risks

  • Shared-file contention: FilterBar.ts (Groups 1→2) and BrowseGrid.test.ts (Groups 2→4) must be edited in dependency order, not concurrently — do not parallelize these two pairs even though Group 3 can run alongside Groups 1–2.
  • Core Requirement 15's “drop/soften” instruction for glossary.ts's doc-comment intentionally has no exact target text (spec-audit Finding 3, Low) — Group 1 step 1.2 gives the implementer discretion by design.
  • The reset()-collapse test added in Group 4 is planner-sourced, not spec-CR-sourced — flagged so it isn't mistaken for scope creep; it closes an existing, already-approved Success Criteria bullet.
