TL;DR

9 task groups, ~52 steps total. Execution order: Group 1 (scaffold/types/git) unblocks everything; Groups 2 (Card), 3 (pure lib logic), and 7 (content pipeline + starter data) then run in parallel; Groups 4 (Browse UI) and 5 (Learn Mode UI) each depend on 2+3 and can run in parallel with each other; Group 6 (AppShell wiring) depends on 4+5; Group 8 (build/deploy/docs) depends on 6+7; Group 9 (test review) closes it out. Theming is folded into each UI group (mockup CSS copied near-verbatim) rather than a standalone pass.

Key Decisions

  • Theming is not a standalone group — palette/tokens seeded once in Group 1, each UI group (2, 4, 5, 6) appends only its own component-scoped rules copied from the mockups.
  • filters.ts, learnAlgorithm.ts, and storage.ts grouped together (Group 3) — pure/stateless, no DOM dependency, independently unit-testable.
  • Content pipeline + starter content is one group (Group 7) — validator and dataset developed together, zero dependency on UI, runs fully in parallel.
  • AppShell (Group 6) scheduled after Browse and Learn Mode, not before — it mounts/toggles already-built views rather than being stubbed against.
  • Per spec-audit fix: Groups 4 and 5 each own and render their own topbar (both including progress-stats); AppShell (Group 6) owns only the bottom tab bar and the two container width variants — never a shared topbar.

Open Questions / Risks

  • Card's public interface (Group 2) must cleanly support both 'full' (Learn Mode) and 'tile' (Browse grid) variants — build and manually verify in isolation before Groups 4/5 start, or both will need rework.
  • Only 3 of 12 category badge colors have mockup precedent (cat-api, cat-java, cat-data) — Groups 4/5 must extrapolate a consistent, accessible-contrast scheme for the rest; only Java renders content this pass, but all 12 chips must still be structurally correct at 0-count.
  • content-pipeline/'s validator (Group 7) has no prescribed library — assume a small hand-written validator; if a schema library is used instead, confirm it's devDependency-only and never imported into src/.

Standards Compliance

No .maister/docs/standards/ directory exists. Conventions come from implementation/spec.md's Implementation Guidance:

  • PascalCase for types/component files (Card.ts, BrowseGrid.ts, LearnMode.ts, AppShell.ts)
  • camelCase for lib/utility modules (filters.ts, learnAlgorithm.ts, storage.ts, config.ts)
  • lowercase-kebab-case for GlossaryEntry.id slugs
  • Two-tier CSS custom-property naming (--color-* raw palette → --bg-*/--text-*/--accent-* semantic aliases)
