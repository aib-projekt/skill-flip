TL;DR

Build the full Skill Flip flashcard app — Vite + vanilla TypeScript, client-only static site — exactly per the 8-section authoritative feature spec, plus one addition: a small AppShell.ts for manual Learn/Browse view-swap (no router). This pass ships the complete app, build, deploy pipeline, and content-authoring tooling, but populates data/glossary.json with only a Java-category starter subset (~15-20 terms), not the full ~150-term/12-category glossary. Greenfield repo — no existing code to reuse.

Key Decisions

  • Follow feature-spec.md's 8 sections verbatim as the desired-state target — already implementation-ready, validated against mockups.
  • Add src/components/AppShell.ts: manual view-swap between Learn and Browse, no routing library, no URL/hash state — resolves the gap-analysis finding.
  • Ship a Java-only starter content subset (~15-20 terms, Regular + Senior) as data/glossary.json; full 150-term set is a deferred follow-up using the pipeline built here.
  • Vitest as test framework (pairs with Vite, zero extra config) — spec is silent by design, this is a sensible default.
  • npm as package manager; fresh git init; repo target aib-projekt/skill-flip (Vite base: '/skill-flip/', Pages URL https://aib-projekt.github.io/skill-flip/); MIT license.

Open Questions / Risks

  • Full ~150-term, 12-category content authoring remains a follow-up pass — not part of this pass's completion criteria. A ~15-20 entry starter set still fully exercises every interaction/algorithm path.
  • Per-category badge-color mapping, the 100%-mastery celebratory banner, and exact "Reset progress" placement are implementation-time details the spec itself leaves open — not escalated as decisions.

Goal

Ship a working, deployed, portfolio-quality flashcard web app for reviewing curated Java/Backend engineering terms — flip-card Learn Mode with weighted spaced-style resurfacing, a filterable/searchable Browse grid, bilingual (EN/PL) content, and a documented content-authoring pipeline — built entirely client-side and hosted on GitHub Pages.

User Stories

  • As the Creator/Learner, I want to open the app and immediately resume Learn Mode (no setup step) so that I can review terms in short, frequent study sessions.
  • As the Creator/Learner, I want cards I mark "don't know" to reappear more often than ones I know, so that review time concentrates on my weak spots.
  • As the Creator/Learner, I want to see the Polish translation of a term and its definition on demand (not forced), so the English definition stays primary but a lookup is one tap away.
  • As the Recruiter/Visitor, I want to land on a live, interactive demo and flip/filter/search within seconds with no reading required, so I can quickly assess craft.
  • As the Recruiter/Visitor, I want to browse all terms by category/level with live counts, so I can scan breadth of coverage fast.
  • As the Creator (maintainer), I want clear instructions/tooling for adding new glossary entries, so growing from ~15-20 to ~150 terms later is straightforward and reproducible.

AppShell & topbar ownership — corrected scope (Req. 5)

AppShell owns only the persistent bottom tab bar and the outer container's max-width variant (480px for Learn, 900px "wide" for Browse, per the mockups) — manual show/hide between the two views, no router, no URL/hash state, Learn Mode progress unaffected by switching.

AppShell does not own a shared topbar. Each view owns and renders its own distinct topbar content:

  • Learn Mode's topbar: exit-to-browse icon + progress-stats + reset-progress icon
  • Browse's topbar: brand label + progress-stats

progress-stats (live mastered/shaky/new counts) is rendered in both views' topbars, not Learn Mode only — confirmed by direct inspection of all 4 mockup files: browse-filter-and-grid.html and browse-empty-state.html render identical .progress-stats markup to the Learn Mode screens. The underlying bucket-count computation is shared (one function reads localStorage learn-progress), but each view's own topbar component is responsible for rendering it.

Why AppShell.ts instead of folding into main.ts

Keeps main.ts a thin bootstrap (fetch data, mount shell) and isolates the one piece of app-wide UI state (active view) in a single, testable place — consistent with the spec's existing file-per-concern pattern (e.g. FilterBar.ts separate from BrowseGrid.ts). Minimum addition needed to resolve the gap; no router, no state-management library, no hash-based deep-linking, matching the spec's explicit no-framework/no-state-library discipline.

Technical Approach

Data flow: main.ts fetches data/glossary.json once → validates non-empty array (visible error on failure) → holds in memory → mounts AppShell. AppShell renders LearnMode or BrowseGrid+FilterBar based on active tab; both feed the same Card component via two different queue-construction strategies (filtered list-order subset vs. weighted-random draw sequence).

State boundaries:

  • Filter/search state — in-memory only, resets on reload (deliberate, not persisted)
  • Learn progress — localStorage key skillflip:learn-progress, written immediately on every mark
  • Card view state (isFlipped, direction, isTranslationVisible) — local to each Card instance
  • Active tab — owned by AppShell, in-memory, no persistence (always starts on Learn)

Integration seam requiring care: the shared Card component must accept an ordered queue + index from either call site without knowing which one constructed it — build and verify Card in isolation first, against both mockup screens, before wiring Browse or Learn Mode to it.

Content pipeline boundary: standalone Node/TS tooling, no imports either direction with src/; validate-glossary.ts run manually and as a GitHub Actions pre-deploy gate.

Repo/deploy: fresh git init; root .gitignore merges Node/Vite defaults with existing .idea/.gitignore (preserve .claude/ and .maister/); Vite base: '/skill-flip/'; deploy workflow triggers on push to main; live at https://aib-projekt.github.io/skill-flip/; no secrets/env vars.

Content Scope for This Pass

This implementation builds the complete, production-ready application and tooling — every component, algorithm, style, pipeline script, and deployment step is fully implemented and functional. What is intentionally scoped smaller is the shipped dataset:

  • data/glossary.json ships with ~15-20 hand-curated Java-category entries, spanning Regular and Senior levels, authored/reviewed using the same pipeline being built in this pass — demonstrating the pipeline works, not just documenting it.
  • The full ~150-term, 12-category glossary is explicitly out of scope for this pass — a documented follow-up task reusing validate-glossary.ts and prompt-template.md unchanged.
  • This scoping does not simplify or stub any app logic: filtering across 12 category values still works correctly even when only "Java" has entries; the weighted-draw algorithm, graduation/demotion rules, and search all operate identically regardless of dataset size.

Implementation Guidance

Testing Approach

  • 2-8 focused tests per implementation step group (scaffolding/types, Card, Browse/Filter/Search, Learn Mode, AppShell, content pipeline, deploy/docs)
  • Test framework: Vitest (pairs with Vite, no extra TS config)
  • Prioritize unit tests for pure logic with explicit acceptance criteria: applyFilters, learnAlgorithm (weighted draw, graduation, demotion, previous-card exclusion, full-mastery fallback), storage.ts round-trip
  • Manual/exploratory verification (mockups as reference oracle) for flip/swipe/keyboard interaction, theming, breakpoints
  • Test verification runs only new tests per group, not the entire suite

Standards Compliance

No .maister/docs/standards/ directory exists in this project — confirmed absent, no project-specific standards to reference. Conventions instead come from the authoritative feature spec: PascalCase for types/component files, camelCase for lib/utility modules, lowercase-kebab-case for GlossaryEntry.id slugs, two-tier CSS custom-property naming (--color-* raw → --bg-*/--text-*/--accent-* semantic).

Success Criteria

  • Progress stats accurate and live, rendered in both the Learn Mode topbar and the Browse topbar; reset-progress clears localStorage after confirmation
  • AppShell switches Learn/Browse with no lost progress, no reload/URL change
