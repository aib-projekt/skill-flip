TL;DR

6 task groups, sequenced exactly as spec/gap-analysis/codebase-analysis all converge on: EmptyState extraction → storage.ts persistence → AppShell mediator → FilterBar/BrowseGrid hydration+propagation → LearnMode (largest surface, built last) → final Test Review. Groups 1–2 are independent and can run in parallel; Groups 3–5 are strictly sequential; Group 6 depends on all. 32 steps total, 31 existing tests must stay green throughout, ~15 new tests expected (46 total).

Key Decisions

  • EmptyState extraction sequenced first (Group 1) — pure, self-contained refactor with zero behavior change for Browse; de-risks every downstream group needing the same pattern for Learn Mode.
  • Mutable entries binding budgeted explicitly in Group 5 (step 5.2) — converting const { entries } = options to let currentEntries is a flagged mechanical prerequisite, not left implicit.
  • writeFilterState() uses an explicit object literal — never destructure-and-delete from a full BrowseFilterState, so searchQuery exclusion is structural at the write boundary.
  • Groups 3 and 4 kept separate despite both being "wiring" work — different files, different test files, and Group 4 depends on Group 3's handleFilterChange contract existing first.
  • No dedicated FilterBar.test.ts — accepted spec gap; covered only via BrowseGrid.test.ts integration tests in Group 4.

Open Questions / Risks

  • Group 5 (LearnMode) carries the highest regression risk — most new interaction surface in a file with 6 passing tests already relying on stable entries. Mitigation: sequenced last, after Groups 1–4 are proven stable.
  • theme.css touched only by Group 5 (new .filter-chip class) — Group 1 reuses existing classes verbatim, so no actual file contention.
  • Exact .filter-chip CSS values are fully specified in both mockups' inline <style> blocks (identical in both) — zero ambiguity, literal declaration copied in step 5.6.
